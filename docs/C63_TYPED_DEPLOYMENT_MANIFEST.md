# C63 — Typed Deployment Manifest

- checkpoint: `C63/150`
- target_progress_after_validation: `135/150`
- predecessor: `C62/150`
- phase: Controlled WASM Deployment
- status: implementation_ready_for_validation

## Objective

Introduce the typed dserver-side Deployment Manifest that binds an externally supplied D-Graph context to explicit module/function/artifact assignments and the deployment-mode semantics reserved in C59.

C63 defines and validates the contract only. It does not derive assignments from D-Graph, distribute node slices, acquire artifacts, invoke DATUM, execute WASM, mutate D-Graph, or authorize governed execution.

## Ownership and pipeline position

The manifest belongs to dserver because the architecture remains:

```text
external D-Graph
  -> dserver validation/materialization/planning
  -> Deployment Manifest
  -> node-scoped assignment/distribution (C64)
  -> DATUM artifact corridor (C65+)
```

The external D-Graph remains evidence/input and is not generated by dserver.

## Typed contract

`dserver/src/core/deployment_manifest.rs` introduces:

- `DeploymentManifest`;
- `DeploymentStrategy::{Centralized, Distributed}`;
- `GraphDistribution::{Full, NodeSlice}`;
- `DeploymentAssignment`;
- `DeploymentArtifactIdentity`;
- `DeploymentRuntimeLimits`;
- `DeploymentExecutionBoundary`;
- `build_deployment_artifact_identity(...)`;
- `validate_deployment_manifest(...)`.

The manifest version introduced by C63 is `0.1.0`.

Each assignment binds:

- `assignment_id`;
- `module_id`;
- `function_name`;
- `artifact_id`;
- `artifact_uri`;
- SHA-256 digest;
- content identity `sha256:<digest>`;
- `target_node`;
- optional fuel and timeout metadata;
- optional non-authoritative metadata.

## Deployment-mode invariants

C63 accepts exactly the two pairs reserved by C59:

```text
strategy=centralized
 graph_distribution=full
```

and

```text
strategy=distributed
 graph_distribution=node_slice
```

Crossed combinations fail validation.

For `centralized/full`, all assignments must resolve to the same target node. For `distributed/node_slice`, assignments may target distinct nodes. C63 does not yet create or filter node slices; that is C64.

## Artifact identity invariant

Every assignment carries both SHA-256 and content identity. Validation requires:

```text
content_id == sha256:<normalized_sha256>
```

The helper accepts a raw 64-character SHA-256 or a `sha256:`-prefixed digest and normalizes hexadecimal case.

This contract reuses the C61 content-addressed identity semantics without claiming signature or provenance trust.

## Execution boundary

Every manifest carries an explicit fail-closed execution boundary. Validation requires:

```text
explicit_invocation_required=true
automatic_execution_allowed=false
governed_execution_authorized=false
```

Therefore a valid C63 Deployment Manifest is deployment data/evidence only. It cannot grant authorization and is not itself executable.

## Validation rules

C63 rejects at least:

- unsupported manifest version;
- empty manifest/project identifiers;
- empty assignment list;
- invalid strategy/distribution pair;
- multiple target nodes for centralized/full;
- duplicate assignment IDs;
- empty module/function/target/artifact identifiers;
- malformed SHA-256;
- content-ID/SHA mismatch;
- zero fuel or timeout when specified;
- attempts to disable explicit invocation;
- attempts to allow automatic execution;
- attempts to claim governed execution authorization.
