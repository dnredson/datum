# Phase 138A — Reconciliation Execution Foundation

## Purpose

Phase 138's own architecture audit concluded **DESIGN GATE REQUIRED** because, while a mature governed reconciliation architecture already exists (spanning `dserver` and the separate `DATUM` agent crate), four concrete gaps made a Console "Reconcile/Execute" workflow unsafe to build on top of yet. A focused follow-up trace (Phase 138A.0) then **proved** one of those gaps — a real time-of-check/time-of-use (TOCTOU) defect in the live agent — from production code, with exact file:line evidence. Phase 138A closes that proven gap and the three others the audits judged tractable without a backend rewrite: a stable per-attempt identity, a DMap-native command-side attempt record, and evidence correlation into it. It implements **no Console UI** and **no execute trigger** — those remain Phase 138 proper's decisions.

## Pull-based architecture (unchanged, restated)

`dserver` never pushes anything to a node. It owns governance only: accepted placement authority (`core::ddeploy`), the operational desired-state projection derived from it (`core::operational_dgraph`), reconciliation authorization issuance/validation, and now (Phase 138A) a read model of what the agent reported attempting. The DATUM agent (a separate crate, `DATUM/src/agent/`) is what actually touches a host: it polls `GET /api/v1/nodes/:node_id/operational-dgraph-slice` for desired state, performs local process/container mutation, and POSTs `OperationalEvidenceEvent`s back to `dserver` via `POST /api/v1/operational-evidence`. Acceptance (Phase 137) never deploys — this remains true and unchanged by Phase 138A.

## Part A — the TOCTOU defect and its fix

### The defect (proven, Phase 138A.0 trace)

`run_operational_reconciliation_from_bootstrap` (`DATUM/src/agent/operational_reconciliation.rs`) fetched the reconciliation context (including the authoritative `dgraph_id`/`dgraph_revision` and the authorization) **exactly once per cycle**, validated it once, then processed every desired service in that cycle's loop using that one, now-static snapshot. Every individual mutation boundary (`check_boundary`, called once per M1-M8 container boundary and N1-N6 native-process boundary) freshly re-sampled the wall clock for lease-expiry checking (a deliberate prior fix, "P0-2"), but **never** re-confirmed that the pinned `dgraph_revision` was still the live authoritative one. A proposal accepted on `dserver` mid-cycle (revision 4 → 5) would not be noticed by an already-running cycle, which would keep mutating against the stale revision-4 decision for every remaining boundary in that cycle.

### The fix

`MutationBoundaryContext` gained one new optional field, `live_revision: Option<LiveRevisionPin>`. When set, `check_boundary` — the ONE shared guard every M1-M8/N1-N6/cleanup/rollback boundary already calls — additionally re-fetches the live `dgraph_id`/`dgraph_revision` from the **existing** lightweight `/operational-dgraph-slice` endpoint (no new DServer route) immediately before that specific boundary and compares it against the cycle's pinned values. A mismatch, or any failure to confirm the live value (DServer unreachable, non-success status, malformed response), blocks the boundary with a new, specific, repository-convention-matching code — `BLOCKED_STALE_DGRAPH_REVISION` or `BLOCKED_LIVE_AUTHORITY_UNCONFIRMED` — recorded in the same `MutationBoundaryRecord` evidence trail as the existing `BLOCKED_LEASE_EXPIRED`. An unconfirmed live authority is never treated as permission to mutate (fail-closed).

All three production construction sites of `MutationBoundaryContext` (the native-process per-service loop, the container per-service loop, and `process_cleanup_directives`, which handles both cleanup and rollback since rollback shares the ordinary per-service loop) now populate `live_revision`, so the fix covers every real mutation boundary uniformly, not just create/spawn. Ownership-label protection (container `datum.dmap_*` labels; native-process `ManagedProcessRuntimeStateV1.dmap_ref`) is unchanged and untouched — freshness is additive to ownership proof, not a replacement for it.

### Test coverage

Eleven new tests in `operational_reconciliation.rs`'s existing test module, using a trimmed, locally-defined raw-socket mock DServer (same established pattern as `agent::bootstrap::tests`): matching revision passes; mismatched revision or `dgraph_id` blocks with `BLOCKED_STALE_DGRAPH_REVISION`; unreachable server, non-success status, and malformed body all block with `BLOCKED_LIVE_AUTHORITY_UNCONFIRMED`; expired lease still blocks even when live revision matches (and does so without ever reaching the live-revision network call); and every one of the 14 governed boundary names is proven protected by the same shared guard.

## Part B — stable reconciliation-attempt identity

`reconciliation_attempt_id` (`"reconciliation-attempt:<uuid-v4>"`) is generated exactly once per cycle, immediately after the context fetch succeeds, inside `run_operational_reconciliation_from_bootstrap` — never per service, never derived from `authorization_id` (one authorization can legitimately cover many cycles), never derived from HTTP request identity (the real mutation happens locally/asynchronously to any one request-response). It is carried on `OperationalReconciliationReport` and threaded into the cycle's terminal `OperationalEvidenceEvent` via a new, additive `OperationalEvidenceEvent::with_reconciliation_attempt_id` builder method — every other, pre-138A call site is untouched and keeps emitting `None` for this field, which is omitted from serialized JSON when absent (`skip_serializing_if`).

## Part C — the DMap-native reconciliation-attempt record

`dserver/src/core/reconciliation_attempt.rs` is a new, small, independent read model — explicitly **not** connected to the legacy `deployment_manifest`/`deployment_assignment`/`DeploymentAttemptRecord` lineage (confirmed in the Phase 138 audit to have zero cross-reference to `operational_dgraph`/accepted D-Map authority) and explicitly **not** DMonitor (command-side "what did the agent attempt" stays separate from observation-side "what is actually running/healthy"). Both isolations are proven by a source-text-scan regression test, not merely asserted.

### Attempt scope: node + operational D-Graph, not a singular application or D-Map

One reconciliation cycle is **node-scoped**, not application-scoped: `OperationalReconciliationContext.desired_services` can legitimately span multiple applications' placements on the same node (the operational D-Graph unions every application placed there). An independent review (post-implementation) found the record's original `application_id`/`requested_by` fields were dead in practice — neither `OperationalReconciliationReport` nor `OperationalServiceReconciliationReport` (the only shapes the agent actually serializes into evidence) carries either field — and `application_id` specifically would have been actively misleading had it ever resolved to a value, since taking it from an arbitrarily-chosen first service would misrepresent a cycle that touched more than one application. Both fields were **removed**. For the same reason there is deliberately **no singular `accepted_dmap_ref`** field: the attempt's primary pinned identity is the **operational D-Graph** (`dgraph_id`/`dgraph_revision`) — the same identity the Part A freshness guard itself pins against — not a D-Map, since one cycle is not guaranteed to touch only one. `authorization_id` is kept (and safe to read from any one service in the payload) because exactly one authorization/lease genuinely covers the whole node-scoped cycle, unlike application identity.

### Lifecycle and per-service result states

`ReconciliationAttemptStatus`: `Succeeded | Partial | Failed | Unknown`. An earlier draft also included `Planned`/`Authorized`/`Executing` "for future use"; an independent review found no production path could produce them (the current evidence stream carries exactly one, already-complete, terminal event per cycle) and removed them — this project's own discipline is to never model a state the system cannot truthfully observe, not to keep states for future-proofing. They can be reintroduced once a real event stream actually produces them. No `Converged`/`Healthy`/`Running` state exists here; that remains Phase 139's authority.

`ReconciliationActionResult`: `NoOp | Mutated | Blocked | Unknown` — deliberately narrower than the task's own suggested `Created/Started/Replaced/Removed` baseline. The agent's internal `execution_status` vocabulary is free text, not a shared enum between the two crates; re-deriving a precise action class from it here would be guessing. The fold uses only the two reliable, structurally-guaranteed signals every service result carries (`host_mutation_performed: bool`, and whether the status text matches this codebase's established `blocked_*` convention) and reports `Unknown` rather than fabricate anything finer. The raw `execution_status`/`message` strings are retained verbatim alongside the classification, so nothing is lost to this conservative collapse.

Overall attempt status is derived deterministically from the per-service results: all succeed (NoOp/Mutated) → `Succeeded`; a mix including any Blocked → `Partial`; all Blocked (none Mutated/NoOp) → `Failed`; anything ambiguous (an Unknown present and nothing else proves success, or no services at all) → `Unknown`, never silently promoted to Succeeded or Failed. `side_effects_performed=true` with no per-service breakdown at all is recorded as `Mutated`/`Succeeded` rather than `Unknown` — the event itself attests a mutation happened, so reporting `Unknown` here would understate, not overstate, certainty.

### Truncation is explicit, never silent

`MAX_SERVICE_RESULTS_PER_ATTEMPT` (500) bounds how many per-service results one fold ingests from a single payload. An independent review found the original `.take(500)` discarded any excess silently. The fix: a `services_truncated: bool` field (on both the full record and its recent-attempts summary) is set the first time a payload exceeds the bound, is **sticky** — a later, smaller/well-formed fold can never clear it — and, whenever set, the derived status is **capped below `Succeeded`** (to `Partial`) even if every retained service result looks fine, since a full-success claim is not provable over data known to be incomplete. Proven by dedicated tests (exceeding the bound, staying at the bound, and stickiness across folds).

### Folding and ordering

`fold_evidence_into_attempt` is a pure function: given the optional existing record and one evidence event, it returns the next record or an error. It rejects (never silently drops or re-applies) a `sequence` at or below the record's `last_applied_sequence` — the duplicate/out-of-order guard — and rejects a `project_id`/`node_id` that disagrees with the existing record for the same attempt id (identity must never drift across folds). `started_at_utc` is set once and never moves on a later fold; `finished_at_utc`/`status`/`services`/`services_truncated` update with each fold. `OperationalEvidenceEvent.sequence` is a single counter local to one agent **process run** (reset only by a restart, which also means fresh `reconciliation_attempt_id`s), shared across every event kind that process emits — the fold's ordering guard only ever compares sequences within one attempt id's own history, so interleaved unrelated event kinds consuming intermediate sequence numbers cannot incorrectly reject a legitimate later event for that attempt.

### Persistence

Reuses the **established** `dserver` generic domain-JSON SQLite store (`storage::control_state::{load_domain_json,persist_domain_json}`), the same mechanism `core::ddeploy`'s own `DDeployStateV1` and `core::operational_dgraph`'s authorizations already use, in the same `datum-control-plane.db`. No Firebase/Firestore, no new persistence mechanism. One domain per attempt (`reconciliation_attempt:<id>`) holds the full record; one domain per project (`reconciliation_attempts_index:<project_id>`) holds a bounded (`MAX_RECENT_ATTEMPTS_PER_PROJECT` = 50), most-recent-first summary index, upserted on every fold. Both survive a `dserver` restart by construction (the same SQLite file every other control-state domain already persists to) — proven by an existing-SQLite-round-trip test, not merely the pure fold function.

### Ingestion, transactionality, and rebuildability (known, disclosed limitation)

`POST /api/v1/operational-evidence` (unchanged route, unchanged request/response shape) now, after successfully appending a freshly-posted event, checks whether it carries a `reconciliation_attempt_id`; if so, it folds the event (read directly from the already-parsed request payload, not reloaded from storage) into that attempt's record and refreshes its project's index. A fold failure is logged, never surfaced as a failure of the evidence POST itself — the evidence event is already durably accepted at that point; the attempt projection is a best-effort derived view over it, not the source of truth.

This is **not** one atomic transaction: event persistence and attempt folding are two separate writes. Event-write-succeeds-then-fold-fails (including a crash in that window) is possible; fold-succeeds-without-a-prior-event-write is structurally impossible (folding only runs after a confirmed `Inserted` outcome). Critically, **the attempt read model is not rebuildable from stored event history today** — `reconciliation_attempt_id` is read directly from the live POST payload at fold time and is not persisted as a queryable column on the general `operational_evidence` SQL table, so a lost fold cannot be recovered by replaying stored events. This is an accepted scope boundary for Phase 138A, not an oversight: the attempt record is explicitly a best-effort secondary projection, nothing safety-relevant depends on it, and it can be made rebuildable later (by adding that column, a small migration) without changing anything about the freshness guard or the governed mutation path itself. DMonitor ingestion is untouched and uninvolved throughout.

### Crash-before-terminal-event (known, disclosed limitation)

Because exactly one, terminal, evidence event per cycle carries the attempt correlation (see "Lifecycle" above), an agent that performs real host mutations and then crashes (or whose final POST is simply lost) *before* that terminal event is sent leaves `dserver` with **no attempt record at all** for that cycle, despite the mutation having genuinely happened. This is a real, disclosed observability gap, not a safety gap: the mutation itself was already governed by the unchanged authorization/freshness/ownership checks, and the agent's own local identity state (persisted native-process records, Docker labels) means the **next** cycle will correctly detect and report the true current state — just not correlated to the specific attempt that originally produced it. Closing this (e.g., an attempt-start event emitted before the first mutation) is deliberately left for a future phase: Phase 138A's scope is the TOCTOU fix, stable identity, and a first command-side read model, not full crash-recovery/exactly-once semantics, which the original Phase 138 audit already identified as a separate, standing architecture risk.

## Part D — read API (no execute endpoint)

`GET /api/v1/reconciliation-attempts/:attempt_id` (project-scoped via `X-Datum-Project`, cross-project requests masked as 404, mirroring `ddeploy`'s own proposal-masking convention) and `GET /api/v1/reconciliation-attempts` (the calling project's bounded recent-attempts index, `limit` narrows further, never widens past the bound). Both are read-only. **No execute endpoint was added.** The live, actual execution trigger remains the `smartsentinel --execute` agent CLI invocation (confirmed in the Phase 138A.0 trace) — Phase 138 proper decides whether/how Console orchestration ever triggers the agent; inventing that trigger now would be scope creep this phase explicitly avoids.

## Part E — day-zero boundary (explicit, unchanged by this phase)

**Phase 138 requires a pre-installed DATUM agent. Phase 138A does not install it, and neither will Phase 138.** No governed installation mechanism exists anywhere in either crate or the repository's scripts/docs (confirmed by the Phase 138A audit's repository-wide search). A clean node must, for now, manually have: the `smartsentinel`/agent binary built and copied on; a `config.toml`; network reachability to `dserver`; Docker installed if container realization will be exercised; and a completed bootstrap/resource-registration cycle. Day-zero installation tooling is out of scope for Phase 138A and Phase 138 both, and is explicitly left for its own future phase rather than folded in here or solved with an ad hoc SSH/remote-install script.

## Part F — shared-runtime restriction (unchanged, restated)

Shared/external/system runtime ownership remains entirely unmodeled in the catalog/service-artifact layer. Phase 138A changes nothing here. Phase 138 MVP, when it exists, may therefore only safely target **project-dedicated `container`** and **project-dedicated `native_process`** placements — the two classes where exact governed ownership is provable (Docker label triple / persisted `ManagedProcessRuntimeStateV1.dmap_ref`). D-Code/WASM invocation (one-shot, not a "desired running" target), shared/external/system runtimes, and composite services remain excluded from continuous reconciliation until their own ownership semantics are designed.

## Part G — container DMonitor producer: confirmed gap, deliberately deferred

Re-confirmed directly from code this phase: `operational_reconciliation.rs` (the file that actually creates/manages containers) has zero references to DMonitor anywhere, while dedicated DMonitor evidence producers exist for native-process (`native_process_dmonitor.rs`), D-Code (`dcode_execution_dmonitor.rs`), and DIoT (`diot_runtime_dmonitor.rs`). Container realization's only evidence trail is the command-side `OperationalEvidenceEvent` stream this phase extends — it produces no observation-authority evidence. This is **Phase 139's gap to close**, not Phase 138A's: it is an observation-producer concern, and command-side attempt state (this phase) must stay structurally separate from observation state, exactly as the architecture invariants require. Nothing in Phase 138A reads, writes, or depends on DMonitor state, and the new attempt record is proven (by test) never mutated by DMonitor evidence.

## Bounds

`MAX_RECENT_ATTEMPTS_PER_PROJECT = 50` (the project attempt index). `MAX_SERVICE_RESULTS_PER_ATTEMPT = 500` (per-attempt service-result count, defense-in-depth — Phase 138A's own dedicated-runtime-only restriction keeps realistic node/application sizes far below this). The read API's `limit` query parameter narrows the index response further but never widens past the stored bound.

## Non-goals (explicit)

No Console UI of any kind. No execute/dispatch endpoint. No agent-installation/bootstrap tooling. No shared/external/system runtime reconciliation. No composite-service realization. No container DMonitor producer. No redefinition of convergence/health (Phase 139's). No change to accepted placement authority, acceptance semantics, or Phase 137's closed scope — proven by test that attempt ingestion never touches `core::ddeploy` state.
